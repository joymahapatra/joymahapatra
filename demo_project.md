# "Demo" Project Repository

Follow these guidelines when creating a Demo project repository.

> **Goal:** Keep the repository lightweight, reproducible, and independent of large datasets and models.


## Caution

* Keep credentials such as keys in environment variables.

```python
import os
api_key = os.environ["API_KEY"]
```

* If using a `.env` file for secrets, add it to `.gitignore`.


## Repository Structure

Use `tree -N` to document the repository structure in `*.md` files.
    
    ```text
    .
    ├── LICENSE
    ├── .gitignore
    ├── README.md
    ├── config.toml
    ├── utils.py
    ├── downloader.py
    ├── app.log
    └── localdata/
    ```

* Use `localdata/` for local project results and generated artifacts.

* External datasets and models must be stored outside and configured through `config.toml`.

    ```text
    /path/to/project/
    └── demo-repo/

    /path/to/data/
    └── datasets/

    /path/to/models/
    └── models/
    ```


## `app.log`

The `app.log` file should contain logs generated by the Demo project. 

* Logging must be implemented using Python's standard `logging` package. 

* Logger configuration and initialization should be managed centrally through `utils.py`. 

    * Use a clear delimiter to separate individual project runs.

    * Define and maintain a consistent log format.

    * Configure both a **stream handler** for console output and a **file handler** for `app.log`.

    * Avoid duplicate log messages when multiple modules initialize or access the logger.

    * Be careful about concurrent or repeated access to the log file.


## `config.toml`

* Store all static project configuration.

* Include project name, author, creation date, external dataset/model paths, preprocessing settings, and model specifications.

* Read configuration using Python's TOML library.

* Avoid placing **dynamic objects, runtime state, secrets, or generated values** in `config.toml`.

* The configuration should contain reproducible, human-readable settings rather than Python objects or runtime-specific state.

## `utils.py`

* Centralize configuration loading, logging, and the `argparse` module.

* All other Python modules must use `utils.py`.

* When the same setting can be provided through both `config.toml` and command-line arguments, establish a clear precedence rule.

    > Command-line arguments should take priority over values defined in `config.toml`. 


## `downloader.py`

* Download datasets and models to their **external configured paths**.

* Use caching to avoid repeated downloads.

* Validate existing files and re-download corrupted or incomplete files when necessary.
